This register describes the Lattice method at an architectural level and the bounded Text to Lattice implementation evidenced in this repository. It does not redistribute the exclusive register profile, certify universal conformance, or convert source tests into deployed proof.

Stable identifiers persist. A claim changes here with cited evidence; a rendered filter, expansion, or downloaded view never changes authoritative state.

Markdown and HTML are deterministic projections of this register. Filtered browser exports are nonauthoritative reading views.

As-built source model

Not a penetration test or deployed attestation

Threat model for the active hah.dev Text to Lattice remote capability: deliberate browser submission, content-free visitor-session setup and one content request under the same origin-wide Web Lock, same-origin API validation, fixed server-side Hugging Face, Nscale, and DeepInfra processing, bounded response handling, and application-level nonretention. Historical WebLLM, Turnstile, and lease controls are inactive and cannot satisfy this model.

Prioritize controls where consequence, realistic plausibility, and lifecycle reuse are jointly high. Preserve uncomfortable residuals: probabilistic semantic drift, external-provider processing and retention, public-endpoint abuse, output capture, supply-chain change, and the gap between source checks and production evidence.

Decision rule: marginal value is proportional to consequence × plausibility × lifecycle value. Unusual findings remain eligible; novelty alone neither promotes nor dismisses them.

Trust boundaries

  • TB-01

    Visitor prose and browser UI

    Untrusted authorized prose becomes inert local state; only an explicit external-processing action may authorize transmission.

  • TB-02

    Browser and same-origin /api/lattice

    After explicit confirmation, one bodyless setup establishes or preserves the signed cookie without quota or provider work; under the same Web Lock exactly one content POST carries text, requested_mode, and schema_version 1. The browser accepts only bounded closed success or error envelopes.

  • TB-03

    API Worker and Hugging Face router

    Server-created prompts cross only to the fixed chat-completions endpoint with a server-only credential and fixed Nscale-served generator and DeepInfra-served verifier roles.

  • TB-04

    Bounded request memory and persistence surfaces

    Source, prompts, candidates, results, and raw provider bodies may exist transiently in request memory but have no application database, object store, cache, queue, raw-content log, or analytics sink.

  • TB-05

    Provider response and public result

    Closed schemas, deterministic checks, size ceilings, and text-only rendering separate untrusted provider output from public outcome claims.

  • TB-06

    Source register and generated documentation

    Escaped deterministic projections expose current claims and clearly marked historical evidence but no visitor content, secrets, or private profile inventory.

SEC-01
Content is transmitted without valid authorization or to an undeclared destination · High marginal value
Vector
Open, edit, validation, prefetch, cancellation, implicit submit, setup failure, blocked cookie storage, automatic retry, a user-controlled target, or a client-visible provider call sends content before deliberate confirmation or outside the named path.
Consequence
Sensitive text leaves the browser contrary to the visitor's choice and the public disclosure.
Plausibility
Ordinary UI, transport, and configuration regressions can create premature, duplicate, or misdirected requests.
Lifecycle value
One named capability and one explicit-action boundary remain reusable across interface and provider revisions.
Classification
Unauthorized or misdirected disclosure is high consequence, integration-plausible, and cheaply prevented by exact request construction and deployment probes.
As built
  • The browser capability is fixed to same-origin POST /api/lattice. Under one origin-wide Web Lock it sends a content-free visitor-session setup followed by exactly one content request containing text, requested_mode, and schema_version 1.
  • Open, edit, validation failure, pre-submit dismissal, and cancellation create no setup or transformation request; a transport or non-204 setup failure prevents the content request; if an accepted setup's HttpOnly cookie is blocked or dropped, the Worker rejects the content request before admission or provider work; terminal failures do not automatically retry.
  • The Worker alone calls the fixed Hugging Face endpoint and fixed Nscale-served generator and DeepInfra-served verifier identifiers.
Required before publication
  • Verify zero network requests before explicit submission on the exact deployed artifact.
  • Capture one successful deployed sequence and the accepted-setup/cookie-blocked failure path; confirm the setup is content-free, exactly one content request follows an accepted setup under the same lock, and the browser contacts only same-origin /api/lattice while Worker egress remains fixed.
Residual boundary
  • The authorized content request necessarily transmits content to Hugging Face, Nscale, DeepInfra, and their infrastructure.
  • Browser extensions, security software, DNS, networks, and provider infrastructure remain outside hah.dev control.

SEC-04
Input or remote inference exhausts bounded resources · High marginal value
Vector
Pathological Unicode, oversized JSON, dense passages, excessive completions, stalled provider calls, repair loops, oversized responses, repeated ordinary-browser use, or distributed valid requests consume bounded browser, Worker, provider, or account resources.
Consequence
The interaction hangs, legitimate visitors exhaust the exact daily admission, provider spend exceeds the intended demonstration budget, or a response exceeds safe client handling.
Plausibility
Realistic for arbitrary public input and third-party inference.
Lifecycle value
Atomic daily admission, centralized ceilings, identity minimization, and fail-closed deadlines bound future pipeline stages and provider revisions.
Classification
Public arbitrary input and paid external work make resource exhaustion ordinary and consequential; an exact global cap has high value even though a cookie-jar limit cannot identify a person.
As built
  • Word, code-unit, request-byte, passage, work-group, completion, provider-output, response-size, and repair ceilings are explicit.
  • The content-free setup makes no quota claim or provider call, and missing-cookie content fails 428 before both. After exact content validation, one atomic claim admits at most 30 transformations globally per UTC day and 3 per cooperating canonical client with an ordinary persistent browser cookie jar per UTC day; quota identity and state use no IP address, browser fingerprint, submitted content, or result.
  • Every admitted attempt counts after disconnect or provider failure without refund, and its pipeline receives no second shared quota claim. At most 32 provider calls per admitted request bounds admitted daily provider exposure at 960 calls.
  • The browser and Worker use 240-second request deadlines; each provider call uses a 60-second deadline. The separate 30-per-60-second path limiter shapes edge bursts.
  • Rate-limited and terminal failures expose bounded machine errors and optional bounded Retry-After without automatic retry.
Required before publication
  • Probe every documented size and timing boundary plus setup/no-admission, missing-cookie pre-admission failure, atomic 30-global/3-cooperating-cookie-jar UTC-day admission, rollover, count-on-failure, no-refund, single-claim, exact cookie, and identity-minimization behavior on the exact deployed API.
  • Verify the 32-provider-call per-admission and 960-call maximum daily provider exposure and measure bounded provider spend and concurrency without claiming availability.
Residual boundary
  • Intentional cookie clearing, blocking, partitioning, or an uncooperative caller remains outside the per-browser identity claim, but the exact global accepted-transformation cap remains authoritative.
  • Distributed callers can consume the finite daily admission, and provider queues and infrastructure behavior remain outside application control.

GATE-02 · Open Release Blocker · High marginal value

Remote API origin, secret, and privacy boundary

Before public activation, the deployed hah.dev origin must expose exactly one named same-origin POST /api/lattice capability. After explicit confirmation and under one origin-wide browser Web Lock, the canonical client must first send a bodyless visitor-session setup with Accept application/vnd.hah.text-to-lattice-visitor-session.v1+json and no Content-Type, then after an accepted 204 setup send exactly one content-bearing request with schema version 1 and only text, requested_mode, and schema_version in its body. A transport or non-204 setup failure must stop before the content request. Client script cannot observe storage of the HttpOnly cookie, so an accepted 204 whose cookie is blocked or dropped may still be followed by that one content request; the Worker must reject a missing cookie as 428 visitor_session_required before Durable Object admission or provider work, while invalid or undeclared cookies fail closed as 403 invalid_request at the same boundary. The setup must establish or preserve the signed cookie without a quota claim or provider call. The API Worker must use exactly the encrypted HF_TOKEN and VISITOR_COOKIE_SECRET bindings; a first isolated setup has no Cookie header, the following content request may carry only the signed opaque __Secure-hah-lattice-api-visitor cookie, and the setup response sets only that cookie with Path=/api/lattice, Secure, HttpOnly, SameSite=Strict, no Domain, and expiry at the next UTC-day boundary. No cookie value may enter retained evidence. The Worker must also use the fixed Hugging Face router with the Nscale-qualified Qwen target and DeepInfra-qualified Llama target, bounded non-reflective errors, Cache-Control: no-store, no application content storage or logging, no automatic retry, no alternate provider or model fallback, and a Content-Security-Policy whose connect-src is 'self'.

Rationale: Raw visitor text leaves the browser at this boundary and a server credential authorizes external model calls. Route, schema, destination, logging, caching, and error-policy drift therefore have high privacy and cost consequences. Source controls are necessary but cannot establish the deployed route, binding, edge response, or provider behavior.

Current active evidence: Source and tests define the exact named remote capability, bodyless custom-Accept visitor-session setup, one content-bearing request under the same origin-wide browser Web Lock, API Worker, fixed provider adapter, HF_TOKEN and VISITOR_COOKIE_SECRET binding names, same-origin credential mode, signed API-scoped quota cookie, 428 visitor_session_required rejection before admission or provider work, bounded request and response policies, no-store behavior, and restrictive browser connection boundary.
